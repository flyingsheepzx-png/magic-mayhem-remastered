# Community build reverse-engineering notes

Observed build SHA-256: `b1eccc46cc16065d57c277fca9c0993635b7b645b3b3b7717759d8bf1c800291`.
`Chaos.exe` is a 32-bit x86 PE with image base `0x400000`. Its file size is 2,076,755 bytes. This hash is the only build examined; all address notes below apply only to it.

## Frame timing

The immutable baseline `CFG/prefs.cfg` contains `MaxFramesPerSec=20`; the installed preference is now 30 by user decision. The string at VA `0x5eb5ac` is read in the preferences load routine around `0x54c361`. The value is bounded to 200 and used to compute `1000 / fps` at `0x54c3c1`–`0x54c3cc`. The save routine references the same key near `0x54cadc`. This demonstrates that simply setting 60 changes a game timer; it does **not** establish that simulation speed, animation and rendering are decoupled. We have not enabled 60 logic in the installed game.

The user clarified the target as 30 logical updates and 60 distinct rendered frames. A short 20/30 comparison observed the loaded preference at VA `0x6de6fd` and derived intervals at VA `0x6de6f9`: `(20, 50 ms)` and `(30, 33 ms)`. The candidate menu scheduler interval at `0x6dbe95` stayed at 50 ms, and candidate menu counters advanced at the same rate in both runs. These counters are not proven gameplay/render counters, so no speed or true FPS claim follows. Diagnostic sessions restore the installed 30 preference after temporary measurements.

The game imports `timeGetTime` and `GetTickCount`; many callers use these clocks. `ddraw.ini` has separate `maxfps` (presentation) and `maxgameticks` controls. A `maxfps` value of 60 therefore does not prove 60 unique game frames. Timing calls and render surface updates still need runtime tracing.

### Main-loop call chain, static evidence (2026-09-27)

- The object constructor at `0x46a10b` installs vtable `0x5c5dd8`. Its `+0x10` slot contains `0x46afc0`. This is the battle scene's candidate per-iteration function, reached through the current-scene dispatch only while that object is active. Runtime tracing has not confirmed the exact scene lifetime or call frequency.
- Within `0x46afc0`, `0x46b71d` traverses unit records in strides of `0xe4b` and calls `0x509e50` for active records; later calls include `0x52a780`/`0x52a9f0` and a distinct cluster around `0x46ba8f`–`0x46bbda` with drawing candidates such as `0x4d6c60`. ### Route call chain, static evidence (2026-09-27)

Direct calls to the route request method at `0x512800` occur at `0x50bd0e`, `0x51cc91`, `0x51d36a`, and `0x5213e6`. It copies a `0x83`-dword result structure from `0x690148` into the unit's `+0x96b` field after calling `0x54b800`. The returned value at unit `+0x97b` controls route active flag `+0xb8b`. The precise coordinate type and route-element layout remain unknown.

Within the route computation at `0x5128a0`–`0x5132ac`, `0x5131b3` calls `0x54b800` with an allowance clamped against globals `0x6df188` and `0x6df18c`; `0x5131c7`–`0x5131d3` subtracts consumed work from both. It records a request fingerprint at `0x6df190`–`0x6df1ac` when work remains (`0x513208`–`0x51323d`). This is evidence of an existing shared route budget and partial-resume mechanism; any replacement must honor it instead of assuming each request is a fresh search. A separate limit at `0x5e174c` seeds the per-request route call in `0x512800`. A unit update at `0x52aab5` reads another route-related limit at `0x5e1748` and invokes `0x5076f0`. These addresses are not yet safe hook signatures.

The offline A* prototype now retains its frontier between budget slices, fairly rotates multiple requests, invalidates stale jobs when the supplied map revision changes, and allows map/goal changes to bypass failure backoff. A caller must still provide exact engine passability, movement costs, map revision, and ownership/visibility policy. Current four-way navigation is only a test model; engine diagonal and movement-type rules have not been recovered. The tests check reachable optimal cost against independent Dijkstra, closed-door recovery, bounded per-tick work, and no illegal model-cell steps. No installed AI behavior changed.

### Follow-up: cell handoff and native skipping

The direct-route regression was narrowed further. `0x510e80` starts a route waypoint, sets motion gate `+0x618=1` at `0x5112f7`, and interacts with old and next cell occupancy through `0x5093e0` and `0x509230`. At segment completion `0x512460` clears the gate at `0x512546`, commits coordinates using `0x5070e0`, then runs occupancy and route-cursor work. Directly overwriting the route before that sequence explains why the duplicated character is a plausible occupancy/interpolation bug, although the exact drawing mechanism remains unproven. The original order handler stores a pending target under `+0xb6f`; at the boundary `0x510010` reissues it through `0x50fae0`. This is a synchronization boundary.

The occupancy calls clarify the A→B transition. At `0x5112cb`–`0x5112eb`, before `+0x618` becomes 1, the engine passes the unit's current grid triple A to `0x5093e0` and the next waypoint triple B to `0x509230`. The former clears occupancy entries only if their owner ID equals this unit's ID; the latter writes that ID and occupancy bits into B and, for some footprint types, adjacent cells or layers. Thus normal in-flight movement releases A and reserves B at segment start, while fine world-pixel position continues between them. This is a qualified occupancy model; special movement/footprint rules need runtime confirmation. A safe mid-edge redirect cannot simply free B: A may already have been claimed, and the current animation and route cursor still describe A→B. A rollback must atomically reclaim a valid anchor cell, release B's reservation, and rebuild interpolation/route state; otherwise finish B and hand off there.

An owned-process test inserted the normal `0x519ae0` action at the order-handler exit only when motion gate `+0x618` was already zero. Unlike the prior `0x512800` experiment, this uses the original budgeted `0x5128a0` caller and its follow-up action. It was still worse: with 600 search allowance, sixteen accepted orders had route-inactive median 0.239 s versus 0.160 s in a same-instrumentation baseline; the longest position-update gap was 0.219 s versus 0.081 s. It was never installed. The trace also shows `0x519ae0` checks action state `+0x688`, animation/action `+0x5fc`, and state `+0x66c`; simply calling it sooner does not guarantee a valid or faster handoff. These exact prerequisites and the planner's shared scratch/result state must be mapped before a queued plan is attempted.

The diagonal timing hypothesis has a stronger static lead. `0x510e80` calls `0x505840` to seed per-segment value `+0xb67`. That function invokes `0x4eaca0`, which doubles the two horizontal deltas and returns a sorted 3-axis weighted distance: twice the largest magnitude plus the middle plus the smallest. For flat one-cell moves, this distance is 4 for cardinal and 6 for diagonal, a **1.5** ratio before later common multipliers and integer rounding. Terrain, unit type, action mode and final interpolation still need runtime checks, so this is a candidate segment-duration ratio, not a measured universal travel-time ratio. It is consistent with the user's observation that diagonal segments can prolong the wait for a new route, but differs from the guessed square-root-of-two factor.

Plaintext configuration includes `SkipFrameEvery=1`, `SkipXFrames=1`, and `MaxSkipXFrames=1`. The loaded max skip at `0x5e1418` participates in timer `0x4e3e40`; its skip flag `0x6e1f00` guards battle presentation at `0x46b91a` and some later timed-effect work. A temporary max-skip zero patch in an owned process (verified loaded value 1 before writing) produced 195 battle-thread primary `BltFast` calls and 195 game-time increments over ten seconds. An unmodified comparison produced 128 such calls and 256 game-time increments. These are call counts, not 60 unique completed images; foreground and scene workload can vary between sessions. They show why turning off skip consumes loop capacity and cannot deliver 30 logic plus 60 drawing on its own. Full-surface hashing was disabled in these trials to avoid its known overhead; the diagnostic DLL/config/saves were restored after each session.

### Disposable mid-segment reroute trial

`runtime/repath_trial.cpp` is a temporary, unit-0-only experiment, injected only into an owned process after the known executable hash and hook bytes are checked. It calls the native planner while the previous A→B edge is in flight, validates a new one-cell edge and swept cells, updates occupancy, calls native segment start, and interpolates from the current world-pixel point toward the new target. A same-layer edge is the main tested case; an unverified reverse floor/cliff edge falls back to the original deferred command. This is not a released pathfinding integration.

In the first sixteen-order `test2` run (`logs/repath-repeat-1790453163333773400.json`), eleven mid-segment redirects were logged and immediate occupancy scans found no mismatch, but the sampled world position jumped `(2208,1568)→(2240,1536)→(2242,1565)` and similarly near `(2208,1504)`. The route cursor reset to 0 on a later route. The experiment's custom interpolation had been cleared only when a motion hook saw a changed cursor, so it could survive completion and collide with the next route. `0x512460` starts segment completion, and its `0x512546` instruction clears motion gate `+0x618`; the trial now clears its private interpolation flag at entry to that completion routine. This is the concrete lifecycle correction, not proof that all effects of the earlier bug are eliminated.

One subsequent sixteen-order run (`logs/repath-repeat-1790453839311530300.json`) logged twelve redirects, three explicit `finish_custom` events, zero ownership mismatches, and no sampled position jump over 12 pixels. First world-position changes after redirected orders were 3.5–9.5 ms. The maximum 0.55 s gap occurred after the unit reached a goal cell and before the next order produced movement, so it is not evidence of a paused mid-segment redirect. ### Attack and animation speed regression: static cause (2026-09-27)

The user reports that some creature attack animations and their attack logic run too fast in the combined 30/60 trial, while positional interpolation is smooth. Static inspection of the hash-verified community executable identifies a concrete time-domain split. In the battle loop, `0x46b71d..0x46b74a` calls unit update `0x509e50` for each active unit on every simulation iteration. Its `0x509f15..0x509f9e` decrements unit fields `+0x8c`, `+0x90` and `+0x94` once per update, independently of global game time `0x6c4830`; other direct per-update decrements occur later, including `+0x744`, `+0xddf`, `+0x748`, `+0x81d`, `+0x819`, `+0x660` and `+0x6b0`. At `0x50a8af..0x50a8c3`, the unit invokes its current action callback from `+0x600`, then animation update `0x54dd60` for the unit's animation object at `+0xbf3`. The animation updater increments its per-frame counter at `+4` unconditionally (`0x54dd69`), advances animation frames when the asset's frame-duration threshold is reached, and can invoke its completion callback at `0x54dddc..0x54dddf`. This is a plausible direct coupling between faster animation and faster attack events for creatures whose damage/action is animation-driven. Other unit behavior checks `0x6c4830` deadlines, which explains why only some creatures may visibly speed up.

The combined trial's `game_time_trial.cpp` paces only the global `0x6c4830` value at 20/33 per 30-Hz iteration; `logic_time_trial.cpp` scales only the movement accumulator at `0x5104d1`. Neither slows the per-unit timers, action callback nor animation frame counter above. The compositor replay calls a private drawing queue and bar drawing without calling `0x509e50` or `0x54dd60`, so the extra displayed frame is not the source of this simulation speedup. The approximate factor cannot be established from static code alone because the original skip scheduler changes achieved update cadence. Next verify with a combat fixture: count `0x54dd60` animation-frame transitions and actual damage/attack events per wall second at native20 versus combined30 for an affected creature.
