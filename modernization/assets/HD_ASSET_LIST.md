## Method

Geometry, colour and letterforms always come from a Lanczos resample of the
original, so nothing is invented where it matters. Qwen-Image 2.1 sees the art
on a canvas whose proportions match one of its fixed presets, and only the
high-frequency band of its output is added, gated twice: a **structure gate**
keeps text strokes, icons, borders and hit targets exact, and a **texture gate**
keeps deliberate flat fills flat. Coverage always comes from the original alpha,
so silhouettes are byte-identical.

Route decides how frames share a canvas:

- **composite** - one conventional image per job.
- **sheet** - an animation container. Frames are aligned to the container box so
  the motion inside each frame is preserved, then split again.
- **atlas** - a tile atlas such as Realm terrain, which has no ordering. Each
  frame gets a tight cell of its own size, which packs 49 frames per canvas
  instead of 9 and roughly doubles the model contribution.

## Measured gain

Edge energy against a plain Lanczos enlargement of the same source to the same
target, measured on samples across every category:

| Category | Route | Gain |
| --- | --- | ---: |
| Grimoire illustration pages | composite | **4.0x** |
| UI full screens, parchment and maps | composite | **3.3x** |
| Realm terrain tiles and scenery objects | atlas | **1.2x** |
| Portraits and small bitmaps | composite | **1.1x** |
| Creature animation frames | sheet | **1.04x** |

The method pays off where there is smooth surface to carry texture. Hard-edged
8-bit pixel art puts nearly all of its signal at edges, exactly where the structure
gate is designed to do nothing, so those categories move only slightly. Terrain at
1.2x is the better part of that group and is included; creature animation is the
weakest and is the one item worth reconsidering before it runs for hours.

## Output layout

`plan` already created the whole tree, so the pack mirrors the installed game
layout and installation is a directory copy:

```
modernization/assets/hd/pack/
  Interface/CharacterScreen/800x600/CharacterScreen.jpg       <- 1920x1440
  Portraits/800x600/Aeetes 800x600.jpg                        <- 160x200
  Creatures/Brownie.spr/0000.png ... plus sprite.json         <- aligned frames
  Realms/Celtic/Plains/Terrain.spr/0000.png ... sprite.json   <- per-frame size
```

- JPEG and BMP keep their container, because the engine already reads them and a
  larger same-format file is the least risky engine test. PCX, TGA and CUR become
  PNG intermediates until a re-encode path is proven.
- Every asset gets a JSON manifest beside it with the source and output SHA-256
  and the Manager job id.
- Sprite containers keep frame index, name, source box, offset and flags in
  sprite.json, which is what a future SPR re-encode needs.

## Install and rollback

Nothing is installed and the engine has not loaded any generated image. The
engine-side gate is unchanged: the game must render a 1920x1440 UI natively and draw
the doubled art at 2x scale, and the coordinate tables in
`Interface/MainScreen/screen (MainMenu).cfg` and `Grimoire.cfg` must scale by
**2.40x** or hit targets will drift.

To install: back up the originals, copy the mirrored tree over the game root, then
check Chinese text, every menu hit target, dark and light backgrounds, tile seams
and save/load. To roll back: restore that backup.

## Open decision

The **sheet** route aligns animation frames to the container box, which is needed
to keep the motion inside each frame, but it leaves a lot of empty canvas: the
Brownie container aligns to 68x67 when its largest frame is 37x57. Terrain showed
that the same sparsity costs about half the model contribution, so animation
containers are probably being held back the same way. Moving them to tight cells
would need the re-encode step to restore the original offsets from sprite.json.
